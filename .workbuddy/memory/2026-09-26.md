### 新发现（已逐条到原文核实）

**P0-1 MCP 服务 SSH 命令注入**：`ServerOpsService.GetServerLogs`(241-253) 与 `QueryServerDb`(284-296) 都把用户参数只做 `Replace("\"","\\\"")` 后拼进命令，再经 `BuildSshArgs`(543-559) 用**双引号**包裹交给远端 bash —— 该转义只对 Windows 本地命令行有效，远端 shell 里 `$(...)`/反引号仍展开。`App.config:16-17` 是 `SSHHost=82.156.108.218` + `SSHUser=root` ⇒ 以 root 执行任意命令。`QueryServerDb` 另无只读约束（可直接 DROP/DELETE 生产库）。修法：走 stdin 传参或对参数做远端 shell 转义（单引号 + `'\''`），并加只读白名单。

**P1-0（原按 P0 拟，复核后下调）`EnsureAllCellsExist()` 追加式补全破坏行主序不变式**：位置索引 = `行号×列数+列号`（`CellCollection.cs:41-44`）→ `Get(row,col)=_list[row*Cols+col]`（:18-24）→ `Table.this[row,col]`（Table.cs:252）。`Syncer.Merge` 重建 Cells 时**是**按 `orderby Row.Index, Column.Index` 行主序（Syncer.cs:2136-2142），但可能留空洞，随后 `if (Rows*Cols != Cells.Count) EnsureAllCellsExist()`（Syncer.cs:2219-2222）而 `EnsureAllCellsExist` 是 **`Cells._list.Add(...)` 追加到末尾**（Table.cs:1065-1092）⇒ 空洞不在末尾时其后所有格位置索引整体错位，`table[r,c]` 静默返回**另一个格**。作者注释自述该路径修的正是"点一次同步坏一堆表"的半合并故障（Syncer.cs:2216-2218），且 `Table.cs:2078+` 的 `TryRepairCellCountBeforeSave` 专门处理"同位置重复 Cell"，说明这块有过真实错乱。关键点：**补全只恢复数量、没恢复顺序，把"取到 null 的响亮失败"换成了"取到别的格的静默错误"**。影响面：`Cells.Get` 11 处 + `Table` 索引器（报告预览、Excel 导入、票据网格、UI 绑定，以及 Table.cs:99 的整表遍历）；**公式引擎未见位置索引使用**。

**未改此条的原因（重要，别再重复判断）**：改法（按行主序重建 `_list`）会天然丢弃"同位置重复 Cell"，必须并入 `TryRepairCellCountBeforeSave` 已有的取舍策略（`Dirty.AnySet()||Status==New` 优先，其次有内容/公式优先），否则会犯作者在 Table.cs:2089-2091 明确警告的"空白格挤掉真实数据"；且无法复现"中间缺格"状态做 A/B 验证 ⇒ 按 `dotnet-db-ab-verify` 铁律（不可验证不下手改核心数据模型）只出报告。

**两个已查实的反证（省得往错方向追）**：① 走 `LoadRowOwnerLoadView`/`CanLoad` 过滤掉中间行**不构成触发**——`Cols` 个格会随该行一起被孤儿清理删掉，计数同步减少、不触发补全；② "同位置重复格"另有来源：Table.cs:2089-2091 注释说明来自"自动补全的空白格与 Pull 下发的真实格按 Id 合并导致同位置共存"，属**先补全、后被覆盖**的时序，与顺序是否错乱无关。
（触发路径最可能是 Merge 的"本地 New 行列 ∩ 服务器 New 行列未完整建格"，**未复现**。另注：Table.cs:658-663 注释明确把"Rows*Cols != Cells"认定为**正常编辑中间态**，故 5 个补全调用点会被日常使用常态进入。）
